# Read-only semantic compatibility consumer

The root API exports `createHarnessSemanticRequirements(input)` and `evaluateSemanticCompatibility({requirements, groundingResult, eligibility?})`. This Harness quality consumer normalizes descriptive requirements and compares concept IDs against imported immutable Ontology grounding results. It does not produce Foundation, candidate sets, packs, snapshots, proposals or catalogs, perform reasoning, approve or publish. Ontology fields remain externally owned; retained legacy schema strings and enum vocabulary are compatibility constants, documented in [provenance](../provenance/semantic-consumer.json).

Requirements need an explicit `foundationDigest` (`sha256:` plus 64 lowercase hexadecimal characters). Optional arrays are `requiredConcepts`, `prohibitedConcepts`, `relationRequirements` and `evidenceRequirements`. Concept rows contain `conceptId`, `metaType`, optional `rationale` and `evidenceRefs`. Normalization retains legacy sorting, last duplicate concept selection, and rejection of required/prohibited overlap. Relation rows contain `subjectConceptId`, `relationType` and `objectConceptId`. A canonical returned requirements object may be supplied again; its schema, authority and digest must agree.

The grounding consumer checks ordinary data descriptors, closed imported DTO structure, digest integrity, known outcomes, consistent counts, presentation bindings and the exact expected Foundation digest before comparison. Limits are 512 results/requirements, 64 evidence references per candidate, 20,000 visited nodes, depth 48 and 524,288 serialized bytes. Accessors, symbols, functions, cycles, sparse/decorated arrays and non-JSON objects reject. Extension-required evidence accepts a closed descriptive `{parentConceptId, definition}` extension observation only. Invalid input throws; it never produces COMPATIBLE.

Missing required or present prohibited concepts produce INCOMPATIBLE first. Otherwise unresolved candidates or empty grounding coverage produce INDETERMINATE. Nonempty fully resolved coverage with satisfied concept requirements and no relation requirements produces COMPATIBLE. Meta types, rationale and evidence requirements retain their legacy descriptive role; the consumer does not invent extra evidence checks. `eligibilityObservation` is a copied object or null and never changes this comparison or overrides Harness eligibility. All output is deeply frozen and input is unchanged.

Historical compatibility normalized relation requirements but did not evaluate them. The new **0.1.0 API deliberately corrects that behavior**: relation-bearing reports add `relationEvaluation: {status: "NOT_EVALUATED", constraints: [...]}` and become INDETERMINATE unless concept checks already produce INCOMPATIBLE. No edges or resolution evidence are fabricated. This is not backward equivalent for relation-bearing reports, and the extended report is not claimed to conform to the frozen legacy report schema. Old reference files and schemas remain untouched. Valid original concept-only, nonempty reports and normalized requirements retain canonical object hashes using the frozen vendor functions. Empty-coverage and stricter malformed-input rejection are additional fail-closed corrections.

## Input prerequisites and native dependency resolution

The consumer accepts the retained legacy grounding-result format (`evopilot-harness-ontology-grounding-result/v1`), not an arbitrary native Ontology delivery or a legacy `OntologySnapshotDTO` directly. The embedding application must configure a trusted resolver for that legacy-format evidence and supply its result with the exact expected Foundation digest. Harness does not fetch or resolve this evidence. Neither the pure API nor `semantic.compatibility.inspect` accepts resolver configuration.

Native asset dependency resolution is a separate implemented path: `createHarnessService(options, {resolveOntology})` accepts a trusted callback, and the parent EvoPilot Preview composition supplies a product-test-validated resolver for exact native published Ontology references. See the [service contract](service.md). That path does not make a new native Ontology delivery identical to the old `OntologySnapshotDTO`, nor does it automatically supply the legacy grounding result. The standalone CLI provides no external resolver and fails required external asset dependencies with `UNAVAILABLE_DEPENDENCY`.

A caller-provided digest establishes local integrity and binding only; it cannot establish owner provenance, publication identity or authority. Compatibility reports are input observations, never publication or eligibility decisions. Harness owns no Ontology producer mutation.

The service exposes exactly `semantic.compatibility.inspect` with required input `{requirements, groundingResult, eligibility}` (eligibility may be null), explicit `{visibility, projectId}` scope and no write fields. After explicit `initialize()`, it returns `{workspaceId, scope, report, authority:false}`. It uses the read transaction and changes no product revision, assets, receipts or audit entries. Extra fields, missing scope and semantic/Ontology mutation operations reject. The pure API remains independent of persistent service imports.

## Verification

Semantic consumer tests (SOURCE-CHECKOUT: `tests/e2e/semantic-consumer.test.mjs`) verify canonical hashes, concept comparison priority, explicit relation non-evaluation, malformed-input rejection and unchanged service revision, receipts, audit and assets. From a source checkout, the pure cases can run read-only with `node --test --test-name-pattern='semantic pure' tests/e2e/semantic-consumer.test.mjs`. The full suite includes the filesystem state test and is part of the verified baseline in the [README](../README.md).

The source checker (SOURCE-CHECKOUT: `scripts/check.mjs`) and specification tests (SOURCE-CHECKOUT: `tests/e2e/specification.test.mjs`) expect `businessOperationsReady === true`, reflecting implemented service availability. Desktop/Host acceptance status is supplied separately in a local report bound to the exact candidate; without that report, no acceptance claim is made. M0 and technical tests do not establish Host acceptance. Machine validation, human decisions, quality evaluation, Runtime business execution and software Release remain separate.
