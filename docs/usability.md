# Usability preflight SDK — v0.8 T1 source candidate

`preflightUsability` is a read-only SDK export from `@evopilot-next/harness`. It is a source candidate; it is not installed by updating documentation, and it does not award L1/L2/L3 or release authority.

Pass `{workspaceId, scope, inventoryDigest, currentPins, specification}` and trusted `UsabilityReaders`. `authorize` must grant the exact Workspace/scope. `readInventory` resolves the independently reviewed frozen inventory by digest. `readCitation` resolves exact published native material through the owning service, including access/license disposition, normative authority and actual file bytes. Do not accept these readers from untrusted request JSON. Missing credentials or unavailable material must fail, not return a synthetic placeholder.

The inventory names mandatory questions and behavior IDs independently of supplied answers. L2 includes L1 and requires every applicable facet: inputs, outputs, interfaces, states, preconditions, postconditions, errors, side effects, idempotency, concurrency, recovery, dependencies and environment. A non-applicable facet has a prior reason and review reference in that same inventory; its slot remains in the denominator. The preflight verifies recorded declarations and bytes; it does not authenticate a human or prove that an answer follows semantically from those bytes.

The result retains the functional slice, exclusions, target level, exact inventory/standard pins and gap codes. Readiness is `READY_FOR_ASSESSMENT`, `INCOMPLETE`, `STALE` or `UNSUPPORTED`. `verifiedLevel` is always null and `assessmentStatus` always `NOT_EVALUATED`. L3 requires independent reconstruction/equivalence evidence outside this preflight. These are EvoPilot conventions, not industry certifications; slice results cannot be averaged into a project-wide level.

Input limits: 128 questions, 64 behaviors, 128 distinct citations and 1 MiB JSON. Evidence limits: 1 MiB per file, 4 MiB cumulative, 2 seconds per read and 10 seconds total. Honor each reader's `AbortSignal`; there is no automatic retry. Authorization is checked before reads. Provider errors become stable unavailable codes without copying private exception text. Malformed, duplicate, extra or unknown requirement identities are rejected.

Source and asset pins, environment, dependency closure, oracle and input-manifest digests are freshness inputs. Any mismatch produces `STALE`; historical results stay readable and are not edited. The SDK does not write owner state, publish assets, execute a builder, or create Runtime Goals/Runs. Standalone HTTP consumption, independent grading and controlled reconstruction follow the v0.8 delivery plan.

## Retained assessments

The service's typed `usability` API adds independently reviewed inventories, exact specification storage, semantic reports and retained assessments. These are additive owner records; they do not change native v1 assets or historical publication decisions. First assessment mutation uses state marker 7. Older writers must reject that state; rollback restores a stopped pre-upgrade backup.

Use `usability.inventory.review` to obtain the digest for the concrete inventory and normative-file bindings. `usability.inventory.freeze` verifies a digest-pinned decision reference. `usability.specification.put` stores exact immutable specification bytes. `usability.semantic.review` exposes the full fixed criterion inventory and missing results; `usability.semantic.record` records a concrete reviewed report. A source-derived declaration or a caller PASS does not itself constitute independent semantic evidence. Decision-file integrity does not authenticate the actor; hosts must retain the actual decision provenance.

`usability.assessment.start` fixes the inventory and specification. `usability.assessment.evaluate` first commits a durable claim, then reads trusted current pins and exact published evidence. L1 requires every domain answer; L2 additionally requires all applicable reviewed behavioral facets. Results retain the standard digest, time, assessor, target/verified distinction, full facet count, explicit excluded count, mandatory count, gaps and evidence pins. Complete documents alone cannot award L3.

For an L3 assessment, `usability.assessment.start` may additionally bind `reconstructionEvaluationIds`, an immutable selection of two to four distinct retained oracle evaluation IDs. Every selected evaluation must be COMPLETE/PASS for the same inventory, specification and oracle binding. Harness rereads the original protected Runtime observations and requires unchanged observation/output digests, actual assets-only isolated execution, independent consumers, the same reconstruction plan/executor, and distinct attempt, claim, clean-workspace and receipt identities. Repeating one attempt under different evaluation IDs does not qualify. Legacy observations without Runtime execution identity remain readable and cannot certify L3. No request can supply its own grade or observations.

Only an assessment satisfying all L1/L2 semantics and all selected reconstruction checks records `verifiedLevel: L3`. Its `reconstructionEvidence` contains the exact immutable oracle result digests. Missing evidence is incomplete/unsupported; a failed oracle is failed; none shrinks the denominator. `usability.assessment.read` rechecks these proofs and the exact semantic decision before exposing a current L3 claim. Changed outputs, revoked/unavailable evidence or stale pins hide that current claim while preserving historical result bytes. Rechecking never executes a builder, mounts a volume or reruns a case.

All writes require `requestId` and `expectedRevision` from `usability.inspect`. Identical replay returns the retained admission and current claim. After interruption it never restarts the evaluator. Inspect the original receipt and assessment; explicitly reconcile the original evaluation to an incomplete result when appropriate. A late provider response cannot overwrite a reconciled claim. Reads require no write envelope. Do not substitute the legacy native revision for the additive assessment/feedback revision.

`usability.assessment.version` reads immutable historical results. `usability.assessment.read` additionally checks current pins and semantic-review identity; drift is stale and unavailable freshness cannot display a current verified level. Changed semantic reports are append-only versions, with a separately updated head. Mixed assessment lists expose no aggregate project grade. These records authorize no Run, project completion, publication or software release.

Trusted SDK configuration supplies `readUsabilityPins` and `resolveFeedbackMaterial`; request envelopes cannot inject them. Missing adapters, malformed evidence, mismatched scope, unavailable publication, timeout, contradictory results and synthetic-only evidence fail closed. Provider exception text is not retained in assessment diagnostics.

## Independent behavior oracle (v0.8 implementation)

Use `usability.oracle.review` with `{inventoryDigest, specificationDigest, oracle}` to inspect an exact profile. It contains mandatory case IDs, normative inputs and expected output/state/error/ordered effects, optional numeric tolerances on output or state, observable-facet mappings and deliberately incorrect control observations. Every applicable observable behavior facet needs coverage; an ineffective negative control is rejected. The oracle content is pinned by the inventory; its separate binding prevents a circular inventory/oracle hash. Freeze the exact binding with `usability.oracle.freeze` and an actual `humanEvidenceRef` for that review. Hidden expectations and controls must remain outside the reconstruction input export.

`usability.oracle.evaluate` takes only `{bindingDigest, attemptId}` plus the usual request ID and owner revision. The host-only `readReconstructionEvidence(context, signal)` provider reads a protected Runtime observation receipt and verifies output bytes; the request cannot supply observations, an executable or a PASS. No provider is configured by default. The receipt pins workspace/scope, attempt, inventory/specification/oracle/input, environment/dependencies, executor and output, and distinguishes actual/synthetic and assets-only/source-assisted inputs. Complete independent isolated actual evidence is necessary for a passing oracle result. This stage does not implement a builder or grant L3 from one oracle result.

Use `usability.oracle.evaluation {id}` for the retained claim and current freshness, `usability.oracle.version {digest}` for immutable result readback, and `usability.oracle.read {digest}` for the exact reviewed profile. All required cases remain in the denominator, including missing, skipped and failed observations. Exact retries return the original claim without another provider call. After interruption, `usability.oracle.reconcile {id}` records incomplete evidence without rerunning anything; a late callback cannot replace that result. Provider failures are bounded and redacted. Current pin drift or missing decision evidence cannot preserve a current PASS. Actual Runtime adapter, clean reconstructions, real pilot and version release acceptance remain required separately.

## Versioned composed-execution evidence

Harness accepts the explicitly versioned reconstruction-observation/v2 envelope alongside unchanged v1 observations. V2 carries the exact execution policy, policy digest, enforcement journal digest, external/unrelated connection counts and complete owned-process closure. The declared isolated flag must agree with this evidence. An owned-loopback run cannot be disguised as an offline v1 observation. The trusted provider must obtain this evidence from Runtime and revalidate the output and current pins; callers still cannot submit their own observations or PASS.

Processing v2 evidence advances Harness state to marker 8, preserving all historical bytes and results. Older readers fail closed. Same-host owner snapshots and relocation accept marker 8, and rollback uses a verified stopped backup. Synthetic evidence, incomplete cases or one passing reconstruction cannot establish L3. The independently fixed full scope, exact semantic decisions and two distinct clean successful attempts remain required.
