# Local Harness service

`@evopilot-next/harness/service` exports `createHarnessService({workspaceRoot, workspaceId}, trustedProviders = {})`. Construction and `capabilities()` are pure. Call `initialize()` explicitly before `execute(request)`; `close()` permanently closes that instance. Use experimental `node:sqlite` on Node 24.14.0. No new dependencies are required.

The workspace must be an isolated canonical absolute path outside source/Git trees, with an existing parent. An empty root can be initialized. Existing workspaces must have the exact shared identity `{schema: "evopilot-workspace/v1", id, canonicalRoot, ownerUid}`. Initialized Ontology state may coexist; Harness touches only its own product state and blobs. Unknown roots, corrupt existing databases, unsafe ownership/modes, symlinks and hardlinked files fail closed.

Requests are closed JSON objects `{operation, scope: {visibility, projectId}, input}`. Mutations additionally require a slug `requestId` and nonnegative integer `expectedRevision`. Unknown keys and operations fail. `workspace.inspect` returns the global Harness revision. A successful mutation atomically commits state, receipt and audit. Repeating a request ID in the same scope with the same operation/input returns the original receipt, regardless of expected revision; changing its intent fails. Errors throw with a `code` and leave the transaction uncommitted.

| Operation | Exact input | Mutation |
| --- | --- | --- |
| workspace.inspect, asset.list, source.list | `{}` | No |
| asset.put | `{asset}` | Yes |
| asset.inspect, asset.review, asset.publish | `{id, version}` | Review/publish |
| asset.decide | `{id, version, reviewDigest, decision, humanEvidenceRef}` | Yes |
| asset.evaluate | `{id, version, evidence, configuration}` | Yes |
| receipt.inspect, evaluation.inspect | `{requestId}` | No |
| source.install | `{sourcePath}` | Yes |
| source.inspect | `{sourceId}` | No |
| source.reinspect | `{sourceId, expectedInspectionDigest}` | Yes |
| legacy.import | `{raw, format, sourceLocator, sourceRevision, sourceVisibility}` | Yes |

Put validates the native Harness asset and matching scope visibility. Draft replacement invalidates review and decision; published versions are immutable. Review binds exact current workspace identity, scope, asset digest, v1 validation and dependency closure. Decide requires `APPROVE` or `REJECT` and a local evidence reference. Publish requires the current exact approved review. Receipts and decisions record the actual OS uid. This is explicit local decision evidence in a single-user trust boundary, not independent multiuser authentication or software release authority.

Dependencies must resolve to exact published deliveries. Profile pins require Components, Bundle pins require Profiles, and EvaluationPack pins require supported Harness assets with intersecting applicability domains. Components cannot contain Harness dependencies. Public references may resolve in the referring project's public scope or project `shared`; multiple matching identities are denied. Private references stay in the same project; public assets cannot reference private assets. Closure traversal rejects cycles, missing dependencies, drift and wrong roles, bounded to depth 64 and 1000 visits. An immutable resolution report is stored separately from the unchanged pure delivery: its frozen `NOT_RESOLVED` report is not rewritten.

The optional second constructor argument permits only a host-configured `resolveOntology` function. It receives `{workspaceId, scope, reference}` and must synchronously return exactly `{reference, published: true, workspaceId, projectId}`. The six reference fields must match exactly; workspace and visibility/project rules apply. Unknown providers, unavailable resolution, drift and asynchronous results fail closed. A returned Promise is rejected with its rejection consumed. Provider configuration is never a JSON request option. The host callback is trusted code; this service supplies no Ontology producer, consumer mutation authority or business completion authority.

Evaluation supports published Components, Profiles, Bundles and EvaluationPacks. Components retain the existing `evaluateHarness` evidence `{id, version, source, values}` envelope and parameter dictionary. For composed roots, `evidence` and `configuration` are dictionaries keyed by canonical serialization of the leaf's exact six-field public reference. Serialize the object with keys in lexical order (`digest`, `id`, `product`, `specVersion`, `version`, `visibility`) and no whitespace; arbitrary labels, root-id-only keys, extra fields and unknown keys are rejected. Values are the unchanged core evidence envelope and parameter dictionary respectively. An omitted configuration entry uses core defaults and records a null supplied configuration digest.

The deterministic closure includes each Component or EvaluationPack with runnable rules exactly once, including a runnable EvaluationPack root. Every supplied leaf uses the unchanged core evaluator. Missing entire evidence entries produce INDETERMINATE with `MISSING_EVIDENCE` and a null evidence digest, without inventing a source. Malformed supplied evidence produces ERROR. Aggregation orders ERROR, FAIL, INDETERMINATE, PASS; explicit disabled applicability yields N/A, all N/A stays N/A, and an empty enabled group is INDETERMINATE. A disabled root suppresses otherwise valid leaf outcomes to N/A, but unknown keys and malformed supplied inputs still fail validation. Warning failures remain FAIL with no actions or version changes.

Reports bind the root reference, closure digest, leaf reference and exact scope, actual supplied input digests, evaluator report digest and individual status. Revalidation verifies every referenced model, delivery and resolution blob and exact published closures, including current external Ontology resolution. The immutable report blob is written before the SQLite transaction commits receipt and audit; failed commits may leave an unreferenced blob as described below. `evaluation.inspect` retrieves the scoped evaluation receipt without replaying evaluation, including after restart. No repair, version change, publication, shell execution, repository execution or log collection occurs.

Source install accepts only exact keys from this package's pinned 101-document archive. Legacy import accepts bounded valid UTF-8 strings in `json`, `yaml`, or explicit `text` format; whitespace and multiline bytes are preserved without trimming. YAML parsing is bounded and rejects custom tags, unsafe aliases and malformed documents. Text is an inert historical record. Recognition includes HarnessBundle, HarnessProfile, HarnessComponent and AssetDeltaProposal with `apiVersion: harness.evopilot.io/v3`, and schemas `evopilot-harness-template/v1`, `evopilot-harness-export/v1`, `evopilot-harness-catalog/v3`. Older Catalog/HarnessCatalog/HarnessLock/HarnessProposal recognition remains source-only. Identity checks follow each format: v3 assets require metadata id/version, templates require top-level id/version, and exports require sourceAsset id/version, a string adapter and an object mapping (optional sourceAsset kind/digest/apiVersion must be nonempty strings). Export mapping semantics are not validated. Catalog lock records require a nonempty catalogId and an entries array; catalog configuration records require nonempty id/lifecycle/source/sourceDigest strings, without requiring entries or an asset version. Malformed required fields produce structural issues and quarantine. Packaged integrity does not bypass these checks. Unknown and foreign Ontology producer labels quarantine regardless of other recognized labels.

Recognition is not legacy semantic or native v1 validation: non-pinned inputs explicitly report `schemaValidation: NOT_EVALUATED`, with `valid: false` even for a recognized preserved source. Identity, version, lifecycle, status and history remain observed data, never converted into approval, activation or a native asset. Source IDs bind origin/revision, format, scope, source visibility and raw digest. Private-to-public import is denied. Every source inspection/list verifies stored raw bytes. No operation reads arbitrary caller paths. The operator reports 146 retained sources (101 public archive and 45 configured), with raw bytes verified unchanged. Six prior classifications require explicit reinspection; this source edit does not mutate those records.

Explicit `source.reinspect` requires the existing sourceId and `expectedInspectionDigest`, computed with the native `sha256(current.inspection)` helper (SHA-256 of stable canonical JSON). It verifies the stored source identity, document digest and original raw bytes before checking that inspection precondition. Packaged provenance is recovered only from an exact owned manifest key, source revision, public source visibility and raw digest, with current archive integrity verification. Caller declarations cannot establish it.

Reinspection recomputes classification without rewriting raw blobs, observed identity, document history or sourceId. Previously absent observed id/version remain null; a catalogId is a separate observation on new imports, not a replacement identity or invented version. Old observation objects are retained exactly. Only the known historical identity-shape mismatch can move a quarantined source to preserved; unknown, foreign and malformed sources remain quarantined. Recognition still grants no approval, publication or inherited authority.

Each changed classification appends an inspectionHistory entry containing original and subsequent inspection/status, before/after inspection digests, actual OS uid, timestamp and requestId. The history is append-only, capped at 16 changes; reaching the cap rejects a further change without dropping history. A no-op returns the current source with a normal receipt and no duplicate history entry. The existing SQLite transaction commits classification, receipt and audit together. Standard request-id replay returns its retained receipt; a new request requires the current inspection digest and workspace revision. Operators should inspect each of the six records and call this operation explicitly after running the filesystem tests, without deletion, reimport or direct production database edits.

State lives at `state/harness/harness.db`, with WAL, FULL synchronization and a 1000 ms busy bound. Owned directories/files require same uid and 0700/0600 modes. Blobs live only under `public/harness` or `private/projects/<id>/harness`. The shared workspace marker retains its exact format. Request JSON is bounded to 512 KiB, 20,000 nodes and depth 48; state holds at most 1000 assets, 1000 sources, 10,000 receipts, 8 MiB state and 32 MiB receipts. Initialization and filesystem blob creation are not part of the SQLite transaction: a crash can leave partial initialization or unreferenced blobs, including blobs created before a failed commit. No automatic repair or garbage collection is provided. Path checking is not a defense against a malicious same-uid process racing filesystem changes.

The generic new-state mechanisms were adapted from the exact staged reference recorded in [state adoption provenance](../provenance/state-adoption.json). No reference or sibling source is imported at runtime. Existing [archive provenance](../provenance/public-assets.json), pure APIs, v1 fixtures and public archive bytes remain unchanged.

Operator verification: run the E2E suite in an environment permitting isolated temporary workspaces. Tests include restart, concurrent child CAS and a test-only interception that kills a child immediately before COMMIT. No production test hook exists. The source checker now verifies exact exports, restricts YAML imports to the two owned importers, and imports/constructs/discovers the service under read-only Node permission. Source checks and in-memory composition tests pass locally; expanded filesystem tests remain for the operator. CLI, MCP, Expert/Host integration, applicable acceptance evidence, operational migration and production/release readiness remain unresolved.
