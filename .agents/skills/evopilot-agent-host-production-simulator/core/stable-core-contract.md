# Stable Simulator Core

The Core owns only the ordinary-human acceptance lifecycle, authority stops, fresh-fixture rules, evidence verdicts and extension composition order. It follows the packaged Digital Expert and deterministic Engine; it never embeds product workflows or assumes that Codex controls a Host UI.

Load `stable-core.json` before selecting extensions. Apply extensions in this order:

1. one Agent Host Adapter declaring either designated-human transport or reviewed automated transport;
2. one Harness Compatibility Adapter selected from inspected protocol and capability evidence;
3. one Target Acceptance Manifest when a governed acceptance target is in scope.

After extension selection, validate one external Candidate Acceptance Binding
for the active attempt. The binding is runtime input, not a Core or Target
extension, and must never be stored in the stable Skill tree.

The Core must remain Host-neutral, version-neutral and Target-neutral. Host controls, platform APIs, product-version branches, acceptance-case identifiers, Source inventories, discovery queries and current-environment failure signatures belong to extensions.

Stop at every exact human gate required by the selected adapter. Navigation language is not a decision, but an exact bounded acceptance authorization may carry machine execution to its next declared stop without repeated navigation prompts. Unknown compatibility, stale bindings, incomplete adapter-declared completion input and uncertain mutations fail closed. A report can classify the selected adapter's completion basis but cannot authorize approval, publication, cleanup or release. The Host Adapter and Target Manifest, not the Core, declare whether a designated-human Host closes from a final range declaration or an automated Host closes from reviewed evidence; one Host cannot substitute for another.
